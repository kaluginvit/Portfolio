## 3. Краткое описание проекта

Автоматизация обрабатывает заявки на бронирование отелей в туристическом агентстве. Клиент оставляет заявку через форму, сценарий проверяет наличие свободного номера в базе, создаёт бронь, меняет статус номера и отправляет клиенту письмо с подтверждением. Если свободного номера нет — клиент получает уведомление, что менеджер предложит альтернативы. Менеджер получает уведомления и ежедневный отчёт по броням.

---

## 4. Бизнес-проблема

Ранее менеджер вручную проверял свободные номера, переносил данные в таблицы, менял статусы и писал клиенту. Это приводило к задержкам в обработке заявок, ошибкам при переносе данных и рискам двойного бронирования — когда один и тот же номер мог быть предложен двум клиентам одновременно.

Автоматизация нужна, чтобы:
- ускорить обработку заявок;
- исключить ручной перенос данных;
- снизить риск ошибок и двойных бронирований;
- сделать процесс прозрачным и управляемым.

---

## 5. Цель автоматизации

После отправки заявки система автоматически сохраняет данные, ищет свободный номер по параметрам (отель, тип, даты), резервирует его, создаёт запись бронирования и отправляет клиенту письмо с подтверждением и инструкцией.

Если подходящего номера нет — клиент получает письмо с отказом, менеджер предложит альтернативы.

Каждый день в 18:00 менеджер получает автоматический отчёт по новым и неподтверждённым броням и номерам со статусом reserved.

**Критерии успеха:**
- заявка обрабатывается без участия менеджера;
- данные фиксируются в базе автоматически;
- статусы номеров обновляются сразу при бронировании;
- дублирующиеся заявки не создают повторных броней.

## 9. Схема процесса

_[Вставить изображение схемы — сконвертировать из `process-diagram.mermaid.md` через mermaid.live или draw.io]_

**Краткое описание логики по шагам:**

1. Клиент заполняет форму бронирования (Tally).
2. Отправка формы запускает сценарий через Webhook в n8n.
3. Сценарий проверяет обязательные поля и нормализует данные (в т.ч. даты).
4. Сценарий проверяет, не была ли такая заявка уже обработана (защита от дублей по `request_id`).
5. Сценарий ищет в Supabase свободный номер (`rooms.status = free`) по отелю, типу номера и диапазону дат.
6. Если номер найден — резервирует его (status → reserved) и создаёт запись бронирования в `bookings`.
7. Клиент получает письмо с подтверждением и инструкцией. Если номер не найден — клиент получает уведомление, что менеджер предложит альтернативы.
8. Каждый день в 18:00 отдельный сценарий формирует отчёт и отправляет менеджеру сводку по бронированиям и номерам со статусом reserved.

**Ветки (развилки):**
- Номер найден / номер не найден
- Заявка-дубль / новая заявка
- Неполные данные / корректные данные

**Точки контроля:**
- Проверка обязательных полей перед обращением к базе
- Защита от дублей по `request_id` перед созданием брони
- Условное резервирование: статус меняется только если номер всё ещё `free`
- Журнал выполнений n8n (Executions) для диагностики

## 10. Реализация сценария в n8n

### 10.1 Общая логика

Создано 2 рабочих процесса:
- **Workflow A** (`pCYE7tn7EhWs3W2D`) — принимает заявку из формы, выполняет валидацию, подбор/резервирование номера, создание брони и отправку письма клиенту.
- **Workflow B** (`C96Oj9KqQ3sNW4m5`) — по расписанию (18:00) формирует ежедневный отчёт и отправляет менеджеру.

### 10.2 Основные шаги сценария

| Шаг | Действие | Инструмент |
|---|---|---|
| 1 | Получение заявки | Tally → Webhook (n8n) |
| 2 | Валидация и нормализация данных | Code-нода (n8n) |
| 3 | Проверка на дубль по `request_id` | Supabase → `bookings` |
| 4 | Поиск свободного номера | Supabase → `rooms` |
| 5 | Резервирование номера | Supabase → `rooms.status: free → reserved` |
| 6 | Создание брони | Supabase → `bookings` (reserved / pending) |
| 7 | Уведомления | Gmail → клиент + менеджер |

### 10.3 Работа с данными

- **Передавались поля:** имя клиента, email, название отеля, тип номера, даты заезда/выезда, найденный `room_id`, цена, статусы.
- **Преобразования:** нормализация дат к формату `YYYY-MM-DD`, формирование `request_id` (конкатенация email + hotel + room_type + даты), формирование текста писем.
- **Условия:** развилка "номер найден / не найден"; фильтры по `hotel_name`, `room_type`, `status`, диапазону дат (`date_from ≤ запрос.date_from`, `date_to ≥ запрос.date_to`).
- **Проверка полей:** в начале сценария; при ошибке — выполнение фиксируется, бронь не создаётся.

## 13. Обработка ошибок и нестандартных случаев

**Предусмотренные ситуации:**
- неполные или некорректные данные во входящей заявке;
- отсутствие свободного номера под заданные параметры;
- повторная отправка одной и той же заявки (дубль);
- временная недоступность Supabase или Gmail.

**Если не хватает обязательных данных:**
Сценарий завершает обработку без создания бронирования. Ошибка фиксируется в журнале выполнений n8n; менеджеру отправляется уведомление о некорректной заявке.

**Если номер не найден:**
Клиенту отправляется письмо о том, что свободных номеров по выбранным параметрам нет, и менеджер предложит альтернативы.

**Если заявка — дубль:**
Проверка по `request_id` в начале сценария; повторная бронь не создаётся.

**Если сервис не отвечает:**
Выполнение фиксируется как ошибка в журнале n8n. При необходимости предусматривается ручная проверка по журналу выполнений.

**Какие ошибки нашли:**
- Merge node в Workflow B использовал устаревший режим `waitForAllInputs` (не поддерживается в n8n Merge v3) — исправлен на `append`.
- Gmail OAuth2 credential требовал повторной авторизации после истечения токена.
- Условие `all().length > 0` в IF-нодах некорректно срабатывало на пустой ответ Supabase.
- В нодах после IF контекст `$json` указывал на предыдущую ноду вместо исходных данных.

**Как исправили:**
- Merge node mode изменён с `waitForAllInputs` на `append` через n8n API.
- Gmail credential повторно авторизован через n8n UI → Credentials → Sign in with Google.
- Все IF-условия заменены на `Object.keys($('Node').first().json).length > 0`.
- Все ноды явно ссылаются на `$('Normalize+Validate').first().json.*`.

## 21. Личное впечатление

Проект получился сложнее, чем казалось на старте. Сам сценарий выглядит логично: форма → вебхук → база → письмо. Но когда начинаешь собирать — вылезают детали, которые в теории незаметны. Как IF-нода ведёт себя на пустом ответе Supabase. Как контекст $json неожиданно указывает не туда. Как Merge node тихо сломался после обновления n8n и об этом никто не сообщил.

Именно эти места оказались самыми ценными. Не потому что приятно ломать голову над ошибкой, а потому что после разбора понимаешь, как всё устроено изнутри — и в следующий раз просто знаешь, где смотреть.

Защита от дублей через request_id — мой любимый узел в этом проекте. Простая идея, но без неё вся система ненадёжна. Люди часто нажимают кнопку дважды.

Курс дал главное: уверенность, что автоматизация — это не магия и не удел разработчиков. Это инструмент, которым можно пользоваться самому, если понимаешь, как думать про процесс.
