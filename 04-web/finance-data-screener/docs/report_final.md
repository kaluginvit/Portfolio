# Отчёт по выпускному проекту

## Название выбранного проекта

**ИИ-скринер финансовых данных** (Вариант C — ИИ-разведчик данных)

---

## Ценность (для кого и зачем)

**Для кого:** аналитики, трейдеры, менеджеры, которым нужны финансовые данные — акции, курсы валют, новости — в виде структурированной таблицы для принятия решений.

**Проблема:** получить нужную выборку с MOEX или ЦБ РФ вручную = 10–15 минут специфичных шагов (знать URL API, параметры, названия полей, написать фильтр). Без технических знаний — невозможно.

**Решение:** пользователь пишет запрос на русском языке. LLM строит план сбора, показывает его, и после подтверждения система забирает данные из открытых источников и отдаёт в виде таблицы с графиком и экспортом.

---

## 3 сценария пользователя

**Сценарий 1 — Успешный сбор:**
Пользователь вводит «Все акции с объёмом торгов > 1 млрд рублей». LLM показывает план (источник MOEX, URL, фильтр VALTODAY > 1B). Пользователь нажимает «Собрать» — система возвращает таблицу из 40+ акций с графиком.

**Сценарий 2 — Витрина и экспорт:**
Пользователь открывает раздел «Витрина», выбирает набор данных, смотрит таблицу и график, скачивает CSV для Excel.

**Сценарий 3 — Ручная проверка:**
Пользователь вводит «Акции с хорошими дивидендами». LLM выставляет `needs_review=true` с причиной: «MOEX ISS не содержит данных о дивидендах в реальном времени». Система показывает жёлтый баннер. Сбор не запускается — пользователю предлагается уточнить запрос.

## Точки доступа API

| Метод | Эндпоинт | Назначение |
|---|---|---|
| GET | `/health` | Проверка работоспособности |
| POST | `/datasets` | Создать набор данных |
| GET | `/datasets` | Список наборов |
| GET | `/datasets/{id}` | Один набор |
| POST | `/datasets/{id}/collect` | Запустить сбор данных |
| GET | `/datasets/{id}/records` | Записи набора |
| POST | `/ai/plan_and_collect` | LLM-планирование (строгий JSON) |
| GET | `/audit` | Журнал всех запросов |

---

## Схема данных (таблицы)

**datasets** — контейнеры для наборов данных
`id, name, query, source, created_at`

**records** — финансовые записи
`id, dataset_id, data (JSONB), collected_at`

**agent_runs** — результаты работы LLM-планировщика
`id, dataset_id, query, plan (JSONB), needs_review, confidence, created_at`

**audit_runs** — аудит каждого API-запроса
`id, endpoint, method, status_code, duration_ms, request_body, error_message, created_at`

## ИИ-операция

**Эндпоинт:** `POST /ai/plan_and_collect`

**Схема JSON-ответа:**
```json
{
  "agent_run_id": "uuid",
  "plan": {
    "source": "moex | cbr | rbc",
    "api_url": "https://...",
    "fields_to_keep": ["SECID", "LAST", "VALTODAY"],
    "filters": {"VALTODAY": {"gt": 1000000000}},
    "confidence": "high | medium | low",
    "needs_review": false,
    "plan_steps": ["Шаг 1...", "Шаг 2..."],
    "review_reason": null
  }
}
```

**Температура:** не задаётся явно (библиотека `instructor` использует дефолт модели). Детерминизм обеспечивается Pydantic-схемой через `instructor`, а не температурой.

**Когда нужна ручная проверка (`needs_review=true`):**
- Запрос двусмысленный («лучшие акции», без чёткого критерия)
- Запрашиваемые данные отсутствуют в источниках (дивиденды, криптовалюта)
- `confidence = "low"` — LLM не уверен в правильности URL или фильтра

---

## Память/контекст

Каждый LLM-план сохраняется в `agent_runs` с полем `plan (JSONB)`. Эндпоинт сбора `POST /datasets/{id}/collect` принимает `agent_run_id` и берёт параметры из уже сохранённой записи — не из запроса пользователя повторно. Это обеспечивает разрыв между планированием и исполнением (Review Flow).

---

## Контроль качества

**На входе:**
- Pydantic-схема на каждом эндпоинте (422 при неверных данных)
- `instructor` гарантирует структуру LLM-ответа через retry-логику

**На выходе:**
- `needs_review=true` блокирует автоматический сбор при неуверенности LLM
- Все ошибки коллекторов (недоступный источник, пустой ответ) записываются в `audit_runs`
- 18 pytest-тестов покрывают все эндпоинты: `/health`, CRUD датасетов, аудит

## План внедрения за 1 день

1. Установить Docker Desktop (если не установлен)
2. Получить ключ ProxyAPI на proxyapi.ru (~$2–5)
3. `git clone <repo>` → `cp .env.example .env` → вписать `PROXYAPI_KEY`
4. `docker compose -p screener up --build` — первый билд ~8 минут
5. Открыть http://localhost — система готова к работе

Итого: 3 команды и ~10 минут ожидания.

## Риски и меры снижения

| # | Риск | Мера снижения |
|---|---|---|
| 1 | LLM строит неверный URL → пустой ответ | Коллектор возвращает пустой список, ошибка в `audit_runs`; пользователь видит 0 записей, не крэш |
| 2 | Внешний источник недоступен (MOEX/ЦБ) | Коллектор ловит исключение → 502 с записью в `audit_runs`; система продолжает работу |
| 3 | Утечка `PROXYAPI_KEY` | `.env` в `.gitignore`; в репозитории только `.env.example` без секретов |
| 4 | Источник блокирует server-side запросы | РБК → автоматический fallback на TASS RSS; задокументировано в `decisions.md` |
| 5 | SSL-перехват корпоративного антивируса | `verify=False` в httpx (данные публичные); для production — заменить на корректный CA bundle |
| 6 | Кириллица в пути ломает `docker compose` | Всегда использовать `-p screener`; задокументировано в README и `decisions.md` |
| 7 | LLM возвращает неверный JSON | `instructor` делает автоматический retry до 3 раз; при провале → `needs_review=true` |

## Сложности и как решал

**1. Кириллица в пути к проекту**
`docker compose` не мог определить имя проекта → падал с ошибкой "project name must not be empty". Решение: добавить флаг `-p screener` во все команды.

**2. РБК заблокировал server-side запросы**
Qrator антибот возвращал 307 с HTML-челленджем вместо RSS. Решение: автоматический fallback на TASS RSS с 100 записями.

**3. MOEX ISS возвращает данные в двух секциях**
`securities` (название, SECID) и `marketdata` (цена, объём) — разные секции одного ответа. Решение: merge по совпадению длин (`dict.update()`), т.к. обе секции возвращают одинаковое количество строк в одном порядке.

**4. asyncpg привязан к event loop в тестах**
При `asyncio_mode=auto` каждый тест создаёт новый loop → asyncpg-соединение из предыдущего loop недействительно. Решение: создавать engine `function-scoped` внутри каждого теста, не в `session`-фикстуре.

**5. SSL-перехват антивируса внутри Docker**
Корпоративный антивирус перехватывает HTTPS внутри контейнеров → `CERTIFICATE_VERIFY_FAILED` при запросах к MOEX/ЦБ. Решение: `verify=False` в httpx и feedparser (публичные данные, риск приемлем).

## План развития

1. **Фоновые задачи** — Celery + Redis для длинных сборов (сейчас сбор синхронный, таймаут при >100 записей)
2. **Авторизация** — JWT + multi-user: каждый пользователь видит только свои датасеты
3. **Расписание сборов** — cron-задачи для регулярного обновления (например, курсы ЦБ каждый день в 12:00)
4. **Расширение источников** — investing.com, Yahoo Finance, данные ФНС
5. **Уведомления** — алерты при аномалиях (резкий рост объёма, отклонение курса от порога)
6. **Экспорт в Google Sheets** — прямая интеграция вместо CSV-файла
